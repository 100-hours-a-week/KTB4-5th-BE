# 작업 지시 (2026-10-17 정리본)

## 목표
BE가 수락한 이미지 분석 요청이 반드시 COMPLETED 또는 명시적 FAILED로 끝나도록 BE→AI 전달을 DB 큐로 바꾼다.
전송량 제어 방식을 비교하고, 기존 보고서(`../REPORT.html`)의 문제 중 무엇이 해결·부분 해결·미해결인지, 새로 생긴 문제는 무엇인지 증거로 추적한다.

## 단계 1 — BE (AI는 4a03494 그대로)
- MySQL 큐: 이미지 1장 = 1행. 접수는 저장 후 즉시 202, `discard()` 제거.
- 전송량 제어는 하나의 장치(AI 인스턴스 슬롯)로 구현하고 슬롯 수만 바꿔 비교한다.
  - P(수용량): 슬롯 수 = AI 수용량(소비자 + 대기열). 429가 오면 백오프.
  - W(콜백 피드백): 슬롯 수 = 1. 콜백 저장 → 슬롯 반납 → 다음 1건 전송.
- 상태: PENDING → DISPATCHING → AWAITING_CALLBACK → DONE | FAILED.
  - 처리 기한 도달 시 헬스가 아니라 작업 단위 조회(`GET /ai/v1/analyses/{id}`)로 연장/재전송/실패를 판단한다.
  - 헬스(ready)는 전송 보류에만 쓰고 시도 횟수를 소모하지 않는다.
- 동시성: 단일 행 선점(SKIP LOCKED + lease 토큰 조건부 UPDATE). 갭락에 의존하지 않는다.
- 검증: 단위·통합 테스트 추가, 로컬 전체 테스트 통과. 랩에서 기존 재현 13건과 Q01~Q13을 P·W로 실행하고, 필요하면 부하 실험을 한다.

## 단계 2 — AI (로컬 저장소에서만 변경)
- requestId 멱등 색인, 접수 작업, 콜백 outbox를 AI DB에 영속한다. 202는 커밋 후 응답한다.
- 콜백에 requestId를 포함하고, BE는 requestId 기준으로 수락한다.
- 단계 1과 같은 시나리오를 재실행하고 차이를 기록한다.

## 제약
- PR·push 없음. 로컬 브랜치 커밋만 하며 AI 공동작성 표기를 넣지 않는다.
- 개발·운영 DB는 변경하지 않는다. 마이그레이션 SQL은 커밋에서 빼고 별도 파일로 둔다.
- 프로젝트 컨벤션을 지킨다: 메서드 ≤30줄, 클래스 ≤300줄, `var` 금지, 주석은 이유만, 패키지는 `analysis/presentation·application·domain·infrastructure`.
- 실험용 기본값은 설정으로 바꿀 수 있게 한다: lease 5s, deadline 5s(연장 3회), 최대 시도 5, 전체 기한 60s, tick 1s.

## 산출물
- `SCENARIOS.md` 결과표: 단계·커밋·해결/부분/미해결/새 문제·근거 파일.
- 시나리오별 evidence JSON (HTTP·DB 행·AI 실행 횟수).
- 최종 보고: 수행하지 않은 검증을 성공으로 쓰지 않는다.
