# 구성원 알림 Kafka 전환

## 스키마 결정 상태

2026-11-04 사용자가 `db/migrations/20261103-membership-kafka.sql`과 같은 구조의 DDL을 채택하고 클라우드 담당자에게 전달했다고 확인했다. 냉장고 사건 순번, 참여 회차별 스냅샷과 유일 제약, 전송 진행 테이블, 알림 완료 진행 테이블을 이번 구현의 기준으로 유지한다.

전달 사실과 실제 DB 적용 완료는 구분한다. 적용 환경과 실행 결과는 아직 확인하지 않았다. 선택적 진행 기록 초기화 SQL은 전달한 DDL에 포함되지 않으며, 현재 코드는 기록이 없으면 0부터 시작하므로 필수 작업이 아니다. 기존 관계의 과거 사건 스냅샷은 NULL로 보존한다.

## 동작과 보장 범위

참여·퇴장·강퇴의 업무 데이터가 커밋되면 요청은 성공이다. Kafka 전송, 전송 진행 표시, 알림 저장은 이후 다른 실행·트랜잭션에서 수행한다. 이 후속 처리가 실패해도 참여를 취소하지 않는다. 참여 업무 데이터 저장·커밋 자체가 실패하면 참여는 실패한다.

```text
MembershipService
  → 회차별 참여·종료 업무 기록에 순번·시각·문구·수신자 보존
  → 커밋·응답

별도 전송 작업
  → 같은 업무 기록에서 다음 순번 복원
  → Kafka 트랜잭션 커밋 확인
  → membership_transmissions 전송 위치 갱신

알림 소비자
  → 원본·key·messageId·순번 확인
  → 알림·수신자·membership_notification_progress 함께 커밋
  → Kafka offset 진행
  → 기존 AFTER_COMMIT Redis/SSE
```

별도 Outbox 작업 INSERT를 참여 성공 조건으로 추가하지 않는다. 회차별 업무 기록에는 변경 당시 스냅샷을 보존한다. 이는 복구 원본을 보관하는 DB 비용을 없애는 설계가 아니며, 참여 업무 기록 자체를 저장하지 못한 경우까지 성공을 보장하지 않는다.

수신자는 사건 당시 유효 구성원 중 활성 회원이며 당사자를 제외한다. 이후 구성원·닉네임·회원 상태가 바뀌어도 저장한 스냅샷을 사용한다. 현재 탈퇴한 사용자의 행도 soft delete로 보존하므로 당시 수신 관계를 만들 수 있다. 기존 화면 조회 권한은 바꾸지 않는다. 알림의 표시 시각은 처리 시각이 아니라 사건 발생 시각이다.

강퇴 당사자의 kicked SSE는 기존 커밋 후 경로를 유지한다. 구성원 Web Push는 새로 만들지 않는다. 회원 서비스 탈퇴는 구성원 알림 사건으로 추가하지 않는다.

## 기록과 순서

재참여는 종료된 관계를 되살리지 않고 새 BIGINT PK의 참여 회차를 만든다. 기존 PK·FK는 유지하며, 같은 사용자·냉장고의 종료되지 않은 관계만 하나로 제한한다. 개인 냉장고 관계와 회원당 현재 선택 하나 제약은 유지한다.

기존 냉장고 행 잠금 아래 업무 순번을 부여한다. 롤백된 변경의 순번도 함께 롤백된다. 시작·종료 정보를 같은 참여 행에 보존하며, 과거 관계를 정리·삭제하는 작업은 별도 보존 정책 없이 추가하지 않는다.

Kafka 메시지는 공통 EventEnvelope<MembershipChangeEvent>를 사용한다. 공통 외곽을 바꾸지 않고 업무 종류는 payload의 type으로 구분한다. 이 토픽의 key는 refrigeratorId 문자열이다. 공통 문서의 분석용 userId key를 구성원 토픽에 강제하지 않는다.

messageId는 이름 공간 fridgely:membership:v1과 냉장고 ID·순번으로 결정되는 UUID다. 재전송·원본 복원 때 UUID를 새로 무작위 생성하지 않는다. 업무 원본은 수정하지 않고 전송 위치·소비 완료 위치만 별도로 전진시킨다.

신규 전송과 복구를 한 전송 경로로 처리한다. 앞 배치의 Kafka 커밋과 DB 진행 표시가 확인되기 전 다음 배치로 넘어가지 않는다. DB 진행 표시 실패는 원래 ID로 중복 전달될 수 있으며 소비자가 중복 생성을 막는다. Kafka 커밋 후 DB 진행 표시보다 먼저 알림이 처리돼도 정상이다.

소비자에 DB 대기 메시지 큐를 추가하지 않는다. 선행 순번이 없거나 원본이 잘못되면 건너뛰거나 DLT로 빼지 않고 해당 파티션에서 재시도한다. 같은 파티션의 다른 냉장고도 지연될 수 있다. 알림 보관 정리 뒤에도 완료 위치를 유지하므로 오래된 사건의 재전달로 삭제한 알림을 다시 만들지 않는다.

## 단일 전송 담당과 장애 인계

전송 작업은 별도 단일 스레드를 사용해 기존 푸시·AI 스케줄러를 점유하지 않는다. 한 실행이 끝나지 않으면 다음 작업을 메모리에 계속 쌓지 않는다.

초기에는 하나의 활성 전송 담당만 사용한다. 같은 MySQL primary의 전용 세션에서 GET_LOCK을 획득한 서버만 Kafka producer를 초기화한다. 나머지는 대기한다. 소유권 연결은 DB 풀 한 연결을 사용하며, Kafka 응답 중 업무 행 잠금·업무 트랜잭션은 유지하지 않는다.

동일 환경·역할의 모든 서버는 같은 transactional.id를 쓴다. 새 담당의 initTransactions가 이전 producer를 fence하고 미완료 거래를 정리한다. DB 연결이 끊어진 이전 담당의 늦은 전송을 세션 잠금만으로 막을 수 있다고 가정하지 않는다. 모든 담당이 같은 쓰기 DB와 Kafka 클러스터를 사용해야 한다.

Kafka 커밋 응답이 불확실하거나 DB 표시가 실패하면 다음 배치를 보내지 않고 producer·소유권 연결을 닫는다. 다음 실행이 소유권과 Kafka 거래 상태를 다시 확정하고 업무 기록을 재조회한다.

소비자는 read_committed와 RECORD offset 처리를 쓴다. 예외를 잡고 성공 반환하지 않는다. 업무 오류도 기본 오류 분류로 건너뛰지 않고 재시도한다. 운영에서는 반복 실패·소비 지연을 확인하고 원인을 고친 후 재개해야 한다.

## 설정

| 설정 | 기본값 | 역할 |
| --- | --- | --- |
| MEMBERSHIP_KAFKA_ENABLED | false | 요청에서 직접 알림을 저장하는 대신 업무 변경 스냅샷을 보존 |
| MEMBERSHIP_KAFKA_TRANSPORT_ENABLED | false | 업무 기록의 Kafka 전송 허용 |
| KAFKA_LISTENER_ENABLED | false | 공통 설정의 소비자 자동 시작 허용. 구성원 소비자는 transport-enabled도 필요 |
| MEMBERSHIP_KAFKA_POLL_INTERVAL | 1s | 전송 확인 주기 |
| MEMBERSHIP_KAFKA_BATCH_SIZE | 100 | 냉장고별 한 Kafka 트랜잭션의 최대 사건 수 |

MEMBERSHIP_KAFKA_SCHEDULING_ENABLED=false는 수동·테스트 실행용이며 자동 전송을 멈춘다. KAFKA_ENV는 토픽·그룹·transactional.id의 환경 접두사다. 환경을 섞거나 같은 역할의 transactional.id를 서버별로 다르게 만들지 않는다.

토픽 이름은 ${KAFKA_ENV}.dameokja.refrigerator.membership.v1이다. 토픽은 인프라에서 사전 생성하고 key 직렬화와 파티션 수를 임의로 변경하지 않는다. 운영 파티션·복제·보관·ISR 설정은 실제 클러스터에 맞춰 검증해야 한다. 애플리케이션이 토픽을 생성하지 않는다.

## DB 적용과 전환

DDL은 src/main/resources/db/migrations/20261103-membership-kafka.sql에 있으며 자동 실행하지 않는다. schema.sql은 격리 테스트·신규 환경의 기준이다. 기존 PK/FK와 행을 삭제하지 않는다.

1. 백업 후 구버전 인스턴스와 구성원 변경 요청을 멈춘 상태에서 DDL과 호환 코드를 배포한다. 구버전 관계 재사용 코드와 새 회차 생성 코드를 섞어 실행하지 않는다.
2. 기본 비활성 상태에서 기존 HTTP·알림 동작을 확인한다. Kafka 토픽과 연결을 준비한다.
3. 전송과 소비를 먼저 검증하고, 모든 인스턴스의 캡처 설정을 동일하게 바꾼 뒤 구성원 변경 요청을 재개한다.
4. 참여·퇴장·재참여·강퇴로 업무 순번, 전송 위치, 알림 완료 위치, 기존 SSE를 확인한다.
5. 롤백할 때는 구성원 변경을 잠시 멈추고 캡처된 사건을 먼저 비운다. 동일 호환 빌드에서 캡처를 끄고 직접 알림 경로로 돌아간다. 과거 바이너리·과거 유일 제약으로 바로 되돌리지 않는다.

활성화 이전 기존 관계에는 사건 스냅샷이 없다. 과거 사건을 현재 구성원으로 추정해 발행하지 않으며, 전환 이전의 누락까지 복구 완료했다고 주장하지 않는다.

## 검증

격리 MySQL·Redis에서 회차 보존, 기존 수신 정책, 당시 수신자, 발생 시각, 업무 롤백, 원본 불일치, 선행 순번 누락, 중복 수신·동시 수신·알림 정리 후 재전달을 검증한다.

격리 Kafka에서는 실제 송수신과 read_committed, Kafka 커밋 후 DB 표시 실패에 따른 재전송, 알림 DB 장애 재시도, 브로커 연결 장애, 전송 담당 대기·인계와 이전 producer 차단을 확인한다. DDL은 별도 격리 DB의 기존 행·제약에서 적용 검증한다.

공개 API·운영 Kafka·운영 DB·배포·실기기 QA와 규모별 부하 검증은 별도다. 이를 로컬 통합 테스트 통과와 혼동하지 않는다.
